## 1. Location and naming of journal files (folder, detection, file naming, new-file rules, Fileheader/LoadGame)

### Takeaway
Everything lives in one folder, `<Saved Games>\Frontier Developments\Elite Dangerous`; resolve `<Saved Games>` with `SHGetKnownFolderPath(FOLDERID_SavedGames)` (not `%USERPROFILE%\Saved Games`) because the folder can be redirected. A new `Journal.<local-time-stamp>.<part>.log` is created per game launch (observed) and per 500,000-line rollover (`Continued`); every file starts with a `Fileheader` line whose `gameversion`/`Odyssey` identify the client, and `LoadGame` repeats language/gameversion/build.

### Cited Findings
- Frontier's manual states the journal and the companion files are written to the user's Saved Games folder, e.g. `C:\Users\User Name\Saved Games\Frontier Developments\Elite Dangerous\`, with file name form `Journal.<datestamp>.<part>.log` — [Manual v38 §2.1](https://hosting.zaonce.net/community/journal/v38/Journal_Manual_v38.pdf)
- EDMC resolves the folder as `known_folder_path(FOLDERID_SavedGames) / "Frontier Developments" / "Elite Dangerous"` via `shell.SHGetKnownFolderPath`, and stores `None` if that directory does not exist; a user-configured `journaldir` overrides it — [EDMC config/windows.py](https://github.com/EDCD/EDMarketConnector/blob/main/config/windows.py), [EDMC monitor.py `start()`](https://github.com/EDCD/EDMarketConnector/blob/main/monitor.py)
- Elite Observatory does the same with a hard-coded GUID `4C5C32FF-BB9D-43b0-B5B4-2D72E54EAAA4` and `SHGetKnownFolderPath`, and has a `PROTON` build path `.../compatdata/359320/pfx/drive_c/users/steamuser/Saved Games` (359320 = Steam app id) — [ObservatoryCore LogMonitor.cs](https://github.com/Xjph/ObservatoryCore/blob/HEAD/ObservatoryCore/Utils/LogMonitor.cs)
- Microsoft: FOLDERID_SavedGames = `{4C5C32FF-BB9D-43b0-B5B4-2D72E54EAAA4}`, folder type PERUSER, default path `%USERPROFILE%\Saved Games`, no CSIDL equivalent; documented paths "might not match those on a particular computer because of … later folder redirection" — [KNOWNFOLDERID](https://learn.microsoft.com/en-us/windows/win32/shell/knownfolderid). `SHGetKnownFolderPath` returns a CoTaskMem-allocated Unicode string the caller must free, and can fail if the KNOWNFOLDERID is absent on the system — [SHGetKnownFolderPath](https://learn.microsoft.com/en-us/windows/win32/api/shlobj_core/nf-shlobj_core-shgetknownfolderpath)
- Current file naming (Odyssey/Live client): `Journal.2022-03-15T152503.01.log`; the older Horizons-style name was `Journal.220315152335.01.log`; because of this, a naive name sort is not safe and EDMC picks the newest file by `getctime`. EDMC's filename regex also accepts a `JournalAlpha`/`JournalBeta` prefix — [EDMC monitor.py `_RE_LOGFILE`, `journal_newest_filename`](https://github.com/EDCD/EDMarketConnector/blob/main/monitor.py)
- Elite Observatory parses both stamp forms (`yyMMddHHmmss` and `yyyy-MM-ddTHHmmss`), falling back to LastWriteTime — [LogMonitor.cs `TimestampFromFile`](https://github.com/Xjph/ObservatoryCore/blob/HEAD/ObservatoryCore/Utils/LogMonitor.cs)
- Local install observation: file stamp is LOCAL time of file creation (e.g. `Journal.2026-10-16T171729.01.log` while the in-file `Fileheader.timestamp` was `2026-10-16T15:17:25Z`, host at UTC+2), i.e. the name lags the UTC header time by the UTC offset plus ~4-10 s; in-file timestamps are UTC (`Z`) — [Local](file:///C:/Users/danik/Saved%20Games/Frontier%20Developments/Elite%20Dangerous/)
- New files: the manual says that if a play session gets long the file is closed and a new file with an increased part number is started, with the heading entry repeated, and the `Continued` event is "written if the journal file grows to 500k lines" — [Manual v38 §2.2, §13.6](https://hosting.zaonce.net/community/journal/v38/Journal_Manual_v38.pdf)
- Local observation: each game launch created its own file; launching and quitting at the main menu produced a 221-byte file containing exactly `Fileheader` + `Shutdown` (4 such files within an hour); a 5-hour session was a single 2.2 MB file with 2,521 lines, one `LoadGame` and a final `Shutdown` — [Local](file:///C:/Users/danik/Saved%20Games/Frontier%20Developments/Elite%20Dangerous/)
- Heading entry fields per manual: `timestamp`, `part`, `odyssey` (bool), `language`, `gameversion` (indicates beta), `build` — [Manual v38 §2.2](https://hosting.zaonce.net/community/journal/v38/Journal_Manual_v38.pdf). Local actual keys: `timestamp, event, part, language, Odyssey, gameversion, build`, e.g. `"language":"Spanish/ES","Odyssey":true,"gameversion":"4.4.1.1","build":"r332841/r0 "` (build has a trailing space) — [Local](file:///C:/Users/danik/Saved%20Games/Frontier%20Developments/Elite%20Dangerous/)
- `LoadGame` fields per manual: Commander, FID, Horizons (bool), Odyssey (bool), Ship, ShipID, StartLanded, StartDead, GameMode (Open/Solo/Group), Group, Credits, Loan, ShipName, ShipIdent, FuelLevel, FuelCapacity, language, gameversion, build; language/gameversion/build were added to LoadGame in manual v32 (Odyssey update 5, July 2021) — [Manual v38 §3.8 and ChangeLog](https://hosting.zaonce.net/community/journal/v38/Journal_Manual_v38.pdf). Local actual keys in 4.4.1.1: Commander, Credits, FID, FuelCapacity, FuelLevel, GameMode, Horizons, Loan, Odyssey, Ship, ShipID, ShipIdent, ShipName, Ship_Localised, build, gameversion, language — [Local](file:///C:/Users/danik/Saved%20Games/Frontier%20Developments/Elite%20Dangerous/)
- Observed startup order in 4.4.1.1: `Fileheader, Commander, Materials, Rank, Progress, Reputation, EngineerProgress, LoadGame, GameModeChange, Statistics, ReceiveText, Location, Music, SuitLoadout, Backpack, ShipLocker, Missions, …` (this commander started on foot in a station, so `Loadout` came later after `Embark`; `Cargo` is written after Missions per the manual) — [Local](file:///C:/Users/danik/Saved%20Games/Frontier%20Developments/Elite%20Dangerous/); [Manual v38 §3.1](https://hosting.zaonce.net/community/journal/v38/Journal_Manual_v38.pdf)
- Journal lines are CRLF-terminated, no UTF-8 BOM, and can be very long (longest line in the sample journal: 39,920 bytes, a `StoredModules` event) — [Local](file:///C:/Users/danik/Saved%20Games/Frontier%20Developments/Elite%20Dangerous/)
- Localisation: any `$symbol;` value gets a sibling `<Key>_Localised` UTF-8 string (omitted when identical to the raw value); the observed commander had Spanish `_Localised` strings — [Manual v38 §2.4](https://hosting.zaonce.net/community/journal/v38/Journal_Manual_v38.pdf), [Local](file:///C:/Users/danik/Saved%20Games/Frontier%20Developments/Elite%20Dangerous/)
- EDMC states the `Fileheader` of a new file resets its tracked state (e.g. `NavRoute=None`) and that "language", "gameversion", "build" from `Fileheader` are stored as GameLanguage/GameVersion/GameBuild — [EDMC PLUGINS.md](https://github.com/EDCD/EDMarketConnector/blob/main/PLUGINS.md)

### Inferences
- Robust detection order for a companion app: (1) user override, (2) `SHGetKnownFolderPath(FOLDERID_SavedGames)` + `Frontier Developments\Elite Dangerous`, (3) verify `isdir` and presence of `Journal.*.log`, (4) optionally Proton/Wine paths. The file-name stamp is local time and not reliable for cross-file ordering around DST changes; order by creation time/mtime (as EDMC does) or by the `Fileheader.timestamp` inside the file.
- Treat "one file per launch, `.NN` increments only on rollover" as the working model; I did not verify whether returning to the main menu and re-logging mid-process stays in the same file (the manual says `LoadGame` is written "when loading from main menu into game", which suggests a second `LoadGame` in the same file).

### Gaps
- No documentation found for the exact trigger of file creation (process start vs first menu load); behaviour above is from one machine's logs.
- Whether Steam/Epic/Frontier-store installs differ in folder: all sources found assume the same Saved Games path; Proton path is Linux-only.

## 4. Writing/flushing behaviour and reading pitfalls (and what established tools do)

### Takeaway
The game appends to the journal while holding it open, and Windows change notifications for appended data can lag because NTFS/cached metadata is only reflected when data is flushed. The proven approach is: open read-only with full sharing (`FileShare.ReadWrite`), keep a byte offset, poll at 0.1-1 s (with a FileSystemWatcher only for new-file creation, or a periodic "poke" of the file), consume only complete `\n`-terminated lines, and treat empty/partial Status.json reads as transient.

### Cited Findings
- Microsoft: `FILE_NOTIFY_CHANGE_SIZE` and `FILE_NOTIFY_CHANGE_LAST_WRITE` are detected "only when the file is written to the disk. For operating systems that use extensive caching, detection occurs only when the cache is sufficiently flushed"; the buffer can overflow, in which case contents are discarded and you must re-enumerate — [ReadDirectoryChangesW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-readdirectorychangesw). .NET `FileSystemWatcher` is built on it: buffer overflow loses events, common operations raise multiple events, and antivirus can add extra events — [FileSystemWatcher](https://learn.microsoft.com/en-us/dotnet/api/system.io.filesystemwatcher)
- Elite Observatory (.NET) uses FileSystemWatchers on `Journal.*.??.log`, `Status.json`, `Cargo.json` (NotifyFilter LastWrite|Size), AND runs a "JournalPoke": "Touches most recent journal file once every 250ms … Forces pending file writes to flush to disk and fires change events for new journal lines" by opening and closing the newest journal with `FileShare.ReadWrite`; an alternative polling mode re-reads every 1000 ms. It re-reads whole files and keeps a per-file line index; ancillary JSON files are read after `Sleep(50)` with up to 10 retries (50 ms apart) because "some files are still locked by another process after 50ms" — [LogMonitor.cs](https://github.com/Xjph/ObservatoryCore/blob/HEAD/ObservatoryCore/Utils/LogMonitor.cs)
- SrvSurvey (.NET) watches the current journal with `NotifyFilter = LastWrite | Size` and comments "FileSystemWatcher sometimes gets stale and needs to be poked, forcing a flush of any pending file writes" — its `poke()` opens/closes the file with `FileShare.ReadWrite` (called from Main.cs on a timer); Status.json uses a watcher on LastWrite and a shared-read helper, ignoring empty results — [JournalWatcher.cs](https://github.com/njthomson/SrvSurvey/blob/HEAD/SrvSurvey/game/JournalWatcher.cs), [Status.cs](https://github.com/njthomson/SrvSurvey/blob/HEAD/SrvSurvey/game/Status.cs)
- EDDiscovery: FileSystemWatcher (NotifyFilter FileName only) just enqueues NEW journal files; appended data is found by a 100 ms scan tick (`ScanTick = 100`) that "always gives the old file another go", and when idle for ~30 ticks rescans the folder for new files. The reader opens with `FileShare.ReadWrite`, seeks to a persisted byte position, reads in a 16 KB buffer that doubles for long lines, advances the position only past a complete `\n`-terminated line (strips `\r`), discards a trailing half line and re-reads it next tick, skips leading NUL bytes ("we have seen these"), and closes the stream when no more data — [MonitorWatcher.cs](https://github.com/EDDiscovery/EliteDangerousCore/blob/HEAD/EliteDangerous/JournalStatus/JournalScan/MonitorWatcher.cs), [Scanner.cs](https://github.com/EDDiscovery/EliteDangerousCore/blob/HEAD/EliteDangerous/JournalStatus/Scanner/Scanner.cs), [TravelLogUnitLogReader.cs](https://github.com/EDDiscovery/EliteDangerousCore/blob/HEAD/EliteDangerous/DB/User/TravelLogUnitLogReader.cs). EDD's Status reader reads the whole file with `FileShare.ReadWrite`, only parses when the text is non-empty and differs from the last successful parse, and tolerates invalid JSON ("the json could be crap") — [StatusReader.cs](https://github.com/EDDiscovery/EliteDangerousCore/blob/HEAD/EliteDangerous/JournalStatus/UIScan/StatusReader.cs)
- EDMC (Python): journal thread polls every `_POLL = 1` s while the game is running and `_INACTIVE_POLL = 10` s otherwise; opens the newest file with `open(logfile, 'rb', 0)` (unbuffered), re-seeks to `log_pos` each loop and iterates lines; watchdog's Observer is used only for `on_created` of new journal files (falls back to scanning for the newest file by `getctime` when the emitter dies); no special partial-line buffering (a bad line is logged by the parser); detects the game by scanning processes for a name containing `EliteDangerous` owned by the same user and synthesizes `StartUp` (EDMC started mid-game) and `ShutDown` (process vanished without a `Shutdown` event, e.g. crash) events — [monitor.py](https://github.com/EDCD/EDMarketConnector/blob/main/monitor.py), [PLUGINS.md](https://github.com/EDCD/EDMarketConnector/blob/main/PLUGINS.md)
- EDMC Status.json: watchdog `on_modified` on the folder plus a 1 s polling fallback (`_POLL = 1`); comments "Can get on_modified events when the file is emptied" (it checks `st_size`) and "Can be empty if polling while the file is being re-written"; empty data is skipped — [dashboard.py](https://github.com/EDCD/EDMarketConnector/blob/main/dashboard.py)
- EDMC retries companion files: NavRoute.json (retry when not yet updated or truncated to empty), ShipLocker.json "tried up to 5 times, 10ms apart", and FCMaterials.json with a time-discrepancy check against the journal event — [EDMC ChangeLog.md](https://github.com/EDCD/EDMarketConnector/blob/main/ChangeLog.md), [monitor.py](https://github.com/EDCD/EDMarketConnector/blob/main/monitor.py); 5.13.3 fixed a journal-monitor race when plugin setup was slow ("Awaiting CMDR Login") — [ChangeLog.md](https://github.com/EDCD/EDMarketConnector/blob/main/ChangeLog.md)
- Rust: the `ed-journals` crate depends on `notify = "8.2.0"` with `file_watcher.rs` reacting to Create/Modify kinds (self-described beta); notify on Windows is a wrapper on ReadDirectoryChangesW, so the Microsoft caveats above apply — [rster2002/ed-journals](https://github.com/rster2002/ed-journals)
- Local facts relevant to parsing: CRLF line endings; no BOM; lines up to ~40 KB; a tiny 221-byte journal when the game is closed at the main menu; `Shutdown` is the last line on clean exit — [Local](file:///C:/Users/danik/Saved%20Games/Frontier%20Developments/Elite%20Dangerous/)

### Inferences
- The game's flush behaviour is not documented; the Observatory/SrvSurvey comments imply appended lines can sit in cache so a watcher may fire late. A cheap robust design: poll (stat size, or open+read from offset) every 250-500 ms while the game process exists (1-2 s when idle), plus a directory listing every few seconds for new `Journal.*.log`; never rely on a watcher alone.
- Cheap implementation: keep (path, offset, inode-like creation time); on each tick `fstat` size; if size > offset read new bytes; split on `\n`; keep trailing fragment in a buffer; parse each complete line; on parse failure retry once later before discarding; detect rollover by a newer file with higher `part`/creation time and drain the old file (to its `Continued`) first.
- For Status.json: read-all with shared access, skip if empty/invalid, compare raw text to avoid re-processing; ~250 ms polling is enough for HUD-like data.

### Gaps
- No Frontier statement on journal flush/`fflush` behaviour or file-handle sharing; no direct evidence on `notify` crate behaviour for appended files (inferred from Win32 docs); latency numbers for the game's flushes were not measured.

## 6. What is NOT available locally (must come from online APIs)

### Takeaway
The journal only records what the local client itself experiences, and market/outfitting/shipyard files only exist for the station UI the player has just opened. Anything about other players, other stations' markets, the wider galaxy and the BGS beyond the current system needs online services (Frontier CAPI, EDDN, EDSM, Spansh, Inara).

### Cited Findings
- Market.json is written "when opening commodity interaction screen", Outfitting.json "when accessing the outfitting menu", Shipyard.json "when accessing shipyard in a station" — i.e. only for the station the player is at — [Manual v38 §2.1](https://hosting.zaonce.net/community/journal/v38/Journal_Manual_v38.pdf)
- System/faction data in `FSDJump`/`Location` covers only the system just entered (Factions[], Conflicts[], Powers); `FSSSignalDiscovered`, `Scan` etc. cover only scanned bodies — [Manual v38 §4.8, 4.12, 6](https://hosting.zaonce.net/community/journal/v38/Journal_Manual_v38.pdf)
- Other commanders: the journal has only events about wing/crew/friends (`WingAdd/Join/Leave`, `Friends`, `CrewMemberJoins`, `ReceiveText`) and combat contacts (`ShipTargeted`, `Scanned`, `Interdicted`); no positions of other players — [Manual v38 §13](https://hosting.zaonce.net/community/journal/v38/Journal_Manual_v38.pdf)
- Frontier's CAPI supplies profile/market/shipyard/fleet-carrier data; EDMC pulls it after journal triggers (fleet-carrier CAPI on `CarrierBuy`/`CarrierStats`, throttled to 15 min, responses reported to take up to 20 min), and 4.2.1.2 added construction requirements to CAPI `/market` — [EDMC PLUGINS.md](https://github.com/EDCD/EDMarketConnector/blob/main/PLUGINS.md), [4.2.1.2 notes](https://www.elitedangerous.com/update-notes/4-2-1-2)
- EDMC "feeds this data to various third party sites", combining journal files with Frontier's API — [EDMC README](https://github.com/EDCD/EDMarketConnector/blob/main/README.md)

### Inferences
- Must come online: markets of stations not visited (EDDN/Inara/Spansh/EDSM), system coordinates and bodies for unvisited systems (EDSM/Spansh/EDAstro), full BGS/faction history, Powerplay system-wide state beyond the current system, colonisation construction status of other players' sites unless you are at the depot, other CMDR positions (not exposed at all; only squadron/wing tools like Inara/EDSM flight logs from their own journals).
- Own data absent from the journal but retrievable via CAPI: authoritative full ship/fleet inventory across stations beyond `StoredShips`/`StoredModules` snapshots, carrier cargo/market.

### Gaps
- I did not verify current CAPI endpoint coverage for 2026 or other APIs' terms.

## 7. Live (4.x) vs Legacy (3.8) galaxy, and console players

### Takeaway
Since Update 14 (29 Nov 2022) the game has a Live mode (4.x, Horizons or Odyssey selectable) and a separate Legacy mode (3.8 build). Tools distinguish them by `gameversion` (>= 4.0.0 = Live). Consoles are not covered: the established tools only support PC accounts and the journal is a local PC file set.

### Cited Findings
- Frontier (23 Nov 2022): from Update 14 (29 Nov) 4.0 is the "Live" mode and 3.8 becomes "Legacy Mode" with a separately tracked commander profile, a separate download from the launcher, no new narrative content, and Legacy actions do not affect Live; Odyssey owners can choose Horizons or Odyssey within Live — [Frontier news](https://www.elitedangerous.com/news/elite-dangerous-update-14-and-beyond-live-and-legacy-modes)
- EDMC `is_live_galaxy()` returns true when parsed `gameversion` >= 4.0.0 (Legacy is < 4.0.0; unknown version = treated as not live); Inara accepts only Live data; EDDN and EDSM messages carry gameversion/build; CAPI for Legacy is a different host handled via `cmdr_data_legacy()` — [EDMC monitor.py](https://github.com/EDCD/EDMarketConnector/blob/main/monitor.py), [EDMC ChangeLog.md](https://github.com/EDCD/EDMarketConnector/blob/main/ChangeLog.md), [PLUGINS.md](https://github.com/EDCD/EDMarketConnector/blob/main/PLUGINS.md)
- EDMC treats `Odyssey` as False if the key is absent and `Horizons` comes straight from `LoadGame`; Horizons-era files have the `Journal.YYMMDDHHMMSS.NN.log` name — [PLUGINS.md](https://github.com/EDCD/EDMarketConnector/blob/main/PLUGINS.md), [monitor.py](https://github.com/EDCD/EDMarketConnector/blob/main/monitor.py)
- Manual changelog: v31/v32 (Odyssey May/July 2021) introduced Odyssey fields; the Fileheader example shows `gameversion` "4.0.0.100" and `odyssey` — [Manual v38](https://hosting.zaonce.net/community/journal/v38/Journal_Manual_v38.pdf)
- EDMC: "only of use to PC players … It won't work with PS4 or Xbox accounts" — [EDMC README](https://github.com/EDCD/EDMarketConnector/blob/main/README.md)
- `ed-journals` (Rust) states it focuses on the Live game, version 4 and up — [rster2002/ed-journals](https://github.com/rster2002/ed-journals)
- Frontier's Update 14 post notes console profile copying to PC is a separate process (console is a separate platform/account) — [Frontier news](https://www.elitedangerous.com/news/elite-dangerous-update-14-and-beyond-live-and-legacy-modes)

### Inferences
- Gate Live-only features on `Fileheader.gameversion` major >= 4; for Legacy sessions (3.8) expect no `Odyssey` key, no Odyssey events, and Horizons-style file names (and possibly the same folder, which is why EDMC filters by game version). Beta clients use `JournalBeta.*` names and share Status.json with live, so filter by session start time.
- Console commanders have no local journal on PC; a PC companion cannot serve them (no source states explicitly that consoles write no journal; absence of any console tooling in EDMC and the manual's Windows-only path is the evidence).

### Gaps
- Not verified: whether Legacy (3.8) still receives patches or writes to the identical folder in 2026; the file name pattern used by the Legacy client today; official statement on console journals.
