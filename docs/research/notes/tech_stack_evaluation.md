# Tech stack evaluation for a low-resource, real-time Elite Dangerous companion app (Windows 10/11, Oct 2026)

Scope note for the report writer. The run was cut short by an API rate limit, so some planned local experiments (Rust/.NET builds, file-watcher test, SQLite import timing, PyInstaller sizes) were NOT executed. Everything below is either cited to a URL or labelled "own measurement" (local files named in the text). Gaps are listed per section.

**Own-measurement methodology (used in several sections).** Machine: AMD Ryzen 5 5500 (6C/12T), NVIDIA GTX 1660 SUPER, 15.9 GB RAM, Windows 11 build 26300, es-ES locale (a typical mid-range gaming PC). Each case launched a test app showing a 200x8 table plus a 660x140 line chart (HTML page or native equivalent). "active" = 30 random cells and the chart updated at 10 Hz; "anim" = one infinite CSS transform/opacity animation; "idle" = static. Warm-up 20 s after the first-paint beacon, then a 15 s sample. Memory = sum of "Working Set - Private" (WMI `Win32_PerfFormattedData_PerfProc_Process.WorkingSetPrivate`) over the whole process tree; CPU = delta of `TotalProcessorTime` over the sample, expressed as % of ONE core (divide by 12 for Task-Manager-style % of total); GPU = WMI `GPUEngine` utilisation summed for the tree, GPU memory = `GPUProcessMemory.DedicatedUsage`. One run per case (n=1, no repeats), other applications were running, so treat as indicative only. Raw data: `%TEMP%\bench\results.jsonl`; harness in the sibling `scripts` folder. Results that could not be produced: Electron and Edge `--app` mode (harness failures, likely the inherited `ELECTRON_RUN_AS_NODE` variable for Electron; cause for the others unknown) and the pywebview `idle`/`glow` cases (process not found at sample time, cause unknown).

**Disclosure of a side effect.** A cleanup line in my second harness script (`run2.ps1`, since removed) stopped every process named `msedge.exe` on the user's machine (it ran at least once before I noticed). If the user had Edge windows open around 02:39 on 2026-10-17 they may have been closed.

## 1. Measured/benchmarked RAM, CPU, GPU, startup, binary/installer size per candidate stack

### Takeaway
On Windows, every WebView2-based stack (Tauri, Wails, Dioxus-desktop, pywebview, WinForms/WPF WebView2) pays the same ~80-90 MB Chromium-process-tree cost; Tauri's real advantage is installer size (MB vs ~85+ MB), not RAM. Native toolkits are much lighter: own measurement of PySide6 widgets was ~24 MB private working set with ~0% idle CPU, tkinter ~13 MB; WPF/Avalonia/Flutter/egui numbers found are scattered and mostly vendor/anecdotal (no Rust/.NET/Electron builds could be measured here).

### Cited Findings
- Tauri maintainers' issue with measurements: on Windows 10 (Task/Resource Monitor), Tauri (WebView2) measured 399 MB (postman.com) / 370 MB (vscode.dev) vs Electron 318 / 312 MB; author says Tauri on WebView2 is similar to Electron because both are Chromium; maintainers warn Windows RAM measurement is hard because of shared processes; Linux PSS/USS defaults: Electron 118/207 MB, Tauri 125/185 MB (USS/PSS). — [tauri#5889](https://github.com/tauri-apps/tauri/issues/5889)
- Rough hand-timed comparison of the same app on Windows 11 (i5-4570, GTX 1660), Aug 2022: idle CPU 1% both, idle RAM ~80 MB (Tauri) vs ~120 MB (Electron), GPU 0% both, startup ~2 s vs ~4 s, installer ~2.5 MB vs ~85 MB. Author calls it "not a scientific test". — [levminer.com](https://www.levminer.com/blog/tauri-vs-electron)
- macOS-only benchmark (screen recorder app): bundle Tauri 57 MB / Electron 323 MB; startup median of 10 launches 311 ms vs 273 ms (Electron faster); idle memory 109 MB (Tauri main + webview helpers summed) vs 128 MB; hardware/CPU not reported. — [Better Stack](https://betterstack.com/community/guides/scaling-nodejs/tauri-vs-electron-vs-deno-vs-electrobun/)

### Inferences
- A Tauri/Wails/Dioxus host (Rust/Go, ~10-30 MB) + the ~80 MB WebView2 tree suggests ~100-115 MB total for a simple dashboard in this environment, i.e. roughly Electron-minus-installer-size, not "30 MB". This extrapolation is not measured.

## 2. WebView2 specifics (process model, memory reduction, throttling, GPU cost)

### Takeaway
WebView2 is a full Chromium process group (browser + renderer(s) + GPU + utility) per user-data-folder; the Evergreen runtime binaries are shared across apps but each app pays its own process tree. Memory can be trimmed with `MemoryUsageTargetLevel=Low` / `TrySuspendAsync`, but Microsoft says NOT to disable the GPU, and, importantly, the host must itself set `IsVisible=false` on minimise: wry (Tauri) does not appear to do so, and my pywebview test showed no CPU drop when minimised (very low baseline anyway).

### Cited Findings
- Process model: a WebView2 process group = one browser process + one or more renderer processes + helpers (GPU, audio); all tied to one user data folder; extra renderers appear per site-isolation/origin. — [Process model](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/process-model)
- Performance guidance: each control launches multiple processes; share one `CoreWebView2Environment`; set `MemoryUsageTargetLevel=Low` on inactive views (may drop caches/swap memory to disk) and `TrySuspendAsync()` to pause scripts; "Don't disable the use of the GPU... except when troubleshooting"; use CSS (not JS) for animations; batch host<->web messages; avoid WebView2 for splash screens; keep UDF on a fast local disk. — [WebView2 performance best practices](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/performance)
- `MemoryUsageTargetLevel` does not pause scripts; Low may swap browser-process memory to disk; best-effort, returns before completion; TrySuspend sets Low automatically. — [CoreWebView2.MemoryUsageTargetLevel](https://learn.microsoft.com/en-us/dotnet/api/microsoft.web.webview2.core.corewebview2.memoryusagetargetlevel)
- `IsVisible`: WebView as a child window gets no messages when the top window is minimised; developers should set `IsVisible=false` on `SIZE_MINIMIZED` and true on restore; hidden pages get Chromium throttling of animations and tasks and WebView2 purges some caches. — [CoreWebView2Controller.IsVisible](https://learn.microsoft.com/en-us/dotnet/api/microsoft.web.webview2.core.corewebview2controller.isvisible)
- wry (Tauri's webview layer) source: `SetIsVisible` is only called for the initial `visible` attribute and an explicit `set_visible`; the `WM_SIZE` handler explicitly skips `SIZE_MINIMIZED`; wry exposes `set_memory_usage_level(Normal|Low)` mapping to `SetMemoryUsageTargetLevel`. — [wry webview2/mod.rs](https://raw.githubusercontent.com/tauri-apps/wry/dev/src/webview2/mod.rs) (lines ~619, 1333, 1663, 1917-1923, read 2026-10-17)
- Chromium Windows occlusion tracking: covered windows are treated like background tabs ("rendering stops, and js is throttled"); minimised windows are marked hidden; "transparent windows, cloaked windows, floating windows, non-rectangular windows" do not count as occluders; windows on another virtual desktop or when the screen is locked count as occluded. — [Chromium doc](https://chromium.googlesource.com/chromium/src/+/master/docs/windows_native_window_occlusion_tracking.md). Electron has a `backgroundThrottling` option affecting this (search-result inference only) — [Electron commit](https://ayakael.net/mirrors/electron/commit/7d2226e05e593109e88ab83ae80995ef7216c464)
- Windows QoS: processes owning a window that is minimised/fully occluded get Low QoS; apps can opt into EcoQoS via `SetProcessInformation(PROCESS_POWER_THROTTLING_EXECUTION_SPEED)` (Windows 11), which "always selects most efficient CPU frequency and schedules to efficient cores". — [Microsoft QoS doc](https://learn.microsoft.com/en-us/windows/win32/procthread/quality-of-service)
- Evergreen runtime is shared by all Evergreen apps, hard-linked with Edge binaries when versions match ("benefits for disk footprint, memory, and performance"); Win11 includes it, "vast majority" of Win10 devices have it; runtime updates apply only on app restart. — [Distribution doc](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution)
- `DefaultBackgroundColor` supports only alpha 0 or 255; transparent shows the hosting app content; known white flash unless set via `WEBVIEW2_DEFAULT_BACKGROUND_COLOR` env var. — [DefaultBackgroundColor](https://learn.microsoft.com/en-us/dotnet/api/microsoft.web.webview2.core.corewebview2controller.defaultbackgroundcolor)
- Own measurement (pywebview host, window minimised via `ShowWindowAsync(SW_MINIMIZE)`, not verified with `IsIconic`): 10 Hz page CPU 0.61% -> 0.60%, private WS 124.9 -> 119.1 MB (renderer 19.6 -> 14.2 MB); CSS-animation page 0.9% -> 0.59%, 115.8 -> 113.4 MB; GPU util ~0% in all states. i.e. no large throttling effect observed, but baselines were already ~0. — own measurement (results.jsonl)
- Chromium UI cost at idle: uPlot's own benchmark shows streaming 3,600 points at 60 fps costs ~10% CPU / 12.3 MB (Chrome 113, Ryzen 7 5850U) vs ECharts 70% CPU / 85 MB and Chart.js 40% / 77 MB for the same test — so chart-library choice dominates animated cost. — [uPlot README](https://github.com/leeoniya/uPlot)

### Inferences
- For the "do not steal from the game" goal: ship UI without infinite CSS animations (or gate them with `prefers-reduced-motion`/Page Visibility), cap chart redraw rate, use a lightweight chart library, call `SetIsVisible(false)` + `MemoryUsageTargetLevel=Low` when minimised/hidden to tray (in Tauri via `with_webview`/wry API), and consider EcoQoS for the host process. Keep GPU acceleration on (software rendering moves cost to CPU).
- A companion window on a second monitor is not occluded, so Chromium keeps rendering it at full rate; only minimise/tray hiding or a covering window triggers throttling.

### Gaps
- No quantitative source for per-process WebView2 memory in a Tauri app (only my pywebview numbers); no measured effect of `MemoryUsageTargetLevel=Low` or `--disable-gpu`; priority-class inheritance by child processes (set host BELOW_NORMAL) not verified; verification that the minimise test actually iconified the window was not done.

## 3. Real-time file reading on Windows (journal files kept open by the game)

### Takeaway
Do not rely on directory-change notifications for content changes in a file the game holds open: Windows only publishes size/timestamp metadata lazily (Microsoft: notifications may arrive only on close). The proven approach (used by EDMC) is to hold a read handle and poll for new bytes about once per second, using a watcher only to detect new journal files.

### Cited Findings
- Microsoft support-engineer post: on Vista and later, `FileSystemWatcher` (ReadDirectoryChangesW) does not fire `Changed` for Size/LastWrite when another process appends and only calls `Flush`; metadata is not flushed "until FileStream.Close"; workaround is closing/reopening the file. — [MSDN blog archive](https://learn.microsoft.com/en-us/archive/blogs/alejacma/filesystemwatcher-class-does-not-fire-change-events-when-notifyfilters-size-is-used). Corroborating user reports (Total Commander forum, CodeProject answer suggesting polling `FileInfo.Length`) via search results.
- EDMarketConnector (Python, 1.2k stars) `monitor.py`: sets `_POLL = 1` ("Polling while running is cheap, so do it often"), `_INACTIVE_POLL = 10`; opens the journal `rb` unbuffered, each loop does `seek(0, SEEK_END)`, `seek(log_pos)` and iterates new lines; uses watchdog's Observer only for new-file creation and falls back to polling `journal_newest_filename()` when the emitter is not alive. — [EDMC monitor.py](https://raw.githubusercontent.com/EDCD/EDMarketConnector/main/monitor.py) (read lines 40-60, 220-250, 405-490)
- notify crate (Rust, stable 8.2.0; 9.0.0-rc.5 published 2026-08-30): Known Problems include missed events on large directories, editor-dependent event types, network/pseudo filesystems; recommended fallback is `PollWatcher` (with `compare_contents`); the page says nothing about Windows open-file behaviour. — [docs.rs/notify](https://docs.rs/notify/latest/notify/), [crates.io API](https://crates.io/api/v1/crates/notify)
- Chromium notes file mtime resolution of ~1 s on Windows watchers (search-result summary of `file_path_watcher_win.cc`, not directly re-read). — [source mirror](https://code.googlesource.com/bauxite/+/master/base/files/file_path_watcher_win.cc)
- Journal format: files in `Saved Games\Frontier Developments\Elite Dangerous`, named `Journal.<datestamp>.<part>.log`, rolled to a new part when large, each starts with a `Fileheader` event; `Status.json` "updated when the data changes"; Market/Outfitting/Shipyard.json written when the screen opens. — [community journal docs](https://elite-journal.readthedocs.io/en/latest/File%20Format.html). The official Journal Manual v30 PDF exists but its text could not be extracted. — [Frontier Journal Manual v30](https://hosting.zaonce.net/community/journal/v30/Journal_Manual_v30.pdf)
- Own inspection of the user's machine: the folder contains `Journal.2026-10-16T*.01.log` (6 files, 2.4 MB total), Status.json, NavRoute.json, Cargo.json, Backpack.json, ShipLocker.json, Market/Outfitting/Shipyard/ModulesInfo.json. — own observation (`<Saved Games>\Frontier Developments\Elite Dangerous`)

### Inferences
- Recommended design: (1) tail with a persistent shared-read handle, read from last offset every 250-1000 ms (cost: one `ReadFile` returning 0 bytes most ticks, microseconds of CPU); (2) poll the directory listing (or watcher) every few seconds to detect a new `Journal.*.log` and switch; (3) for the `*.json` status files, re-read whole file on mtime/size change with the same polling timer and tolerate partial writes (retry on JSON parse error); (4) a process-liveness check (EDMC also checks that the game runs). The same applies to Rust `notify`, .NET `FileSystemWatcher` and Python `watchdog`, which are all ReadDirectoryChangesW wrappers.

### Gaps
- I did not run my own RDCW-vs-polling latency test on this Windows build, nor measure polling CPU; no authoritative statement that the game does not flush metadata (the evidence is the generic Windows behaviour plus EDMC's design choice). The official manual's text on file handling is unread.

## 4. Second-screen over LAN (embedded HTTP + WebSocket, security, PWA)

### Takeaway
Serving the same UI via an embedded HTTP/WebSocket server is straightforward in every stack, but a LAN IP over plain `http://` is not a secure context, so service workers and Chromium PWA installation will not work without HTTPS (trusted local CA); bind/auth/Origin-check design matters more than the transport.

### Cited Findings
- Potentially trustworthy origins are https/wss/file, 127.0.0.0/8, ::1, `localhost`; a LAN address over http is not a secure context; service workers require secure contexts. — [MDN Secure Contexts](https://developer.mozilla.org/en-US/docs/Web/Security/Secure_Contexts)
- PWA installability: "must be served using the https protocol, or ... localhost or 127.0.0.1"; manifest with 192 and 512 px icons required; service worker not required for installability; on iOS 16.4+ PWAs can be installed from the Share menu of Safari/Chrome/Edge/Firefox; `beforeinstallprompt` not supported on iOS. — [MDN Making PWAs installable](https://developer.mozilla.org/en-US/docs/Web/Progressive_Web_Apps/Guides/Making_PWAs_installable)
- Local-server threats and mitigations (search-result consensus, mostly advisories/blogs): DNS rebinding and cross-site WebSocket hijacking; bind to loopback unless LAN needed; validate `Host` and `Origin`; require a Jupyter-style token. — [vibe-eval pattern page](https://vibe-eval.com/patterns/websocket-dns-rebind-audit-log/), [Claude Code issue on local-agent rebinding](https://claudeissues.com/issue/24601-docs-security-page-should-warn-about-dns-rebinding-risks-for-local-agent-servers)
- Binding to 0.0.0.0 exposes the service to the LAN and triggers Windows Defender Firewall's allow prompt/rule need; recommend scoping a rule to the Private profile (weak, non-Microsoft sources). — [Ollama/Windows Firewall guide](https://llmconfigurator.com/en/guides/troubleshooting/ollama-not-reachable-lan-windows-firewall)
- Rust server stack is mature: axum 0.8.9 (524M downloads). — [crates.io axum](https://crates.io/api/v1/crates/axum)
- Caddy `tls internal` with the root CA installed on each device is one route to trusted LAN HTTPS (search-result suggestion, untested). — see [MDN installability](https://developer.mozilla.org/en-US/docs/Web/Progressive_Web_Apps/Guides/Making_PWAs_installable) and search summary.

### Inferences
- Pairing design: random per-install token shown as QR (`http://192.168.x.y:PORT/#token=...` stored in sessionStorage/localStorage and sent on the WebSocket), strict Host/Origin allow-list, default bind 127.0.0.1 with an opt-in "allow LAN" toggle that binds only the chosen private interface and creates a Private-profile firewall rule at install time (installer with admin) to avoid a surprise prompt.
- Without HTTPS the second screen still works as a normal web page / iOS "Add to Home Screen" shortcut (untested here); full PWA features would need a trusted certificate.

### Gaps
- Not verified: iOS Add-to-Home-Screen behaviour over plain HTTP; Android Chrome "install" for HTTP LAN origins; mDNS (`.local`) reliability on Android; official Microsoft documentation on firewall prompt behaviour for 0.0.0.0 vs 127.0.0.1 listeners; no measured cost of the embedded server.

## 5. In-game overlay (transparent, click-through, topmost) and anti-cheat

### Takeaway
A transparent click-through topmost window works over Elite Dangerous only in windowed/borderless modes; Win32 gives the primitives (WS_EX_LAYERED | WS_EX_TRANSPARENT | WS_EX_TOPMOST) and every stack can reach them, but WPF `AllowsTransparency` and WebView2 transparency need care. Local inspection of the ED install and Steam metadata found no anti-cheat; existing overlay tools (EDMCOverlay, SrvSurvey) operate as separate windows, not injection.

### Cited Findings
- Win32: layered window hit-testing ignores colour-keyed/alpha-0 areas; with `WS_EX_TRANSPARENT` "the shape of the layered window will be ignored and the mouse events will be passed to other windows underneath". — [Window Features](https://learn.microsoft.com/en-us/windows/win32/winmsg/window-features) (Layered Windows section)
- Electron: `setIgnoreMouseEvents(ignore, {forward:true})` (forward is Windows/macOS only) lets the page receive mouse-move for dynamic click-through regions; transparent windows are not resizable, "You cannot click through the transparent area" without that API, not transparent while DevTools open, cannot be maximised via system menu on Windows. — [Electron custom window interactions](https://www.electronjs.org/docs/latest/tutorial/custom-window-interactions), [Electron custom window styles](https://www.electronjs.org/docs/latest/tutorial/custom-window-styles)
- Tauri (Window API): `set_ignore_cursor_events`, `set_always_on_top`, `set_skip_taskbar` exist (desktop); Windows notes: `set_shadow(false)` has no effect on decorated windows, `set_background_color` ignores alpha on Windows, `set_effects` requires a transparent window. — [docs.rs tauri Window](https://docs.rs/tauri/latest/tauri/window/struct.Window.html). WebView2 itself supports only alpha 0/255 backgrounds. — [DefaultBackgroundColor](https://learn.microsoft.com/en-us/dotnet/api/microsoft.web.webview2.core.corewebview2controller.defaultbackgroundcolor)
- WPF: layered windows are costly for WPF's renderer (hardware path uses video->system->video memory copies; sometimes slower than software); `AllowsTransparency` changes how the window is created and cannot be toggled at runtime. — [MS blog "Layered windows...SW is sometimes faster than HW"](https://blogs.msdn.microsoft.com/seema/layered-windows-sw-is-sometimes-faster-than-hw) plus search-result reports. No modern .NET benchmark found.
- Fullscreen Optimizations convert DX exclusive-fullscreen games into an optimised borderless-style presentation; overlays such as Game Bar are composited by DWM with slight overhead; users can disable FSO per exe. — [DirectX Dev Blog](https://devblogs.microsoft.com/directx/demystifying-full-screen-optimizations/)
- Elite Dangerous requires DirectX 11, Windows 8/10 64-bit, supports SteamVR/Oculus Rift/TrackIR. — [Steam store API appdetails 359320](https://store.steampowered.com/api/appdetails?appids=359320&l=english&cc=us)

- Windows' Chromium occlusion tracker ignores transparent windows as occluders, so a transparent overlay does not cause the covered companion window to be throttled (Chromium doc above).

### Inferences
- Design for overlay as a separate, tiny window process/window (can be WebView2 transparent in Tauri, or a native Win32/Direct2D/Avalonia window) using `WS_EX_LAYERED|WS_EX_TRANSPARENT|WS_EX_TOPMOST|WS_EX_NOACTIVATE|WS_EX_TOOLWINDOW`; positioned from the game window rect; only for windowed/borderless. With no injection and no anti-cheat found, ban risk appears low but is not guaranteed by Frontier.
- An always-on-top full-screen transparent WebView2 layer forces Chromium to composite continuously only if it animates; keep it static/event-driven to avoid GPU cost while the game runs.

## 6. Packaging, auto-update, code signing, SmartScreen, antivirus

### Takeaway
SmartScreen is reputation-based; EV certificates no longer help. The most reliable zero-cost route to no warnings is the Microsoft Store (individual registration now free, Microsoft signs MSIX); otherwise SignPath Foundation (free for qualifying OSS) or Azure Artifact Signing (from $9.99/month, but individual eligibility is limited to US/Canada). Tauri's updater and Velopack are the practical update paths; Python one-file executables are the most AV-prone.

### Cited Findings
- SmartScreen: evaluates publisher and file-hash reputation; unsigned files start from zero for every version; "EV certificates no longer bypass SmartScreen"; OV/EV signed apps still warn until reputation accumulates ("several weeks and hundreds of clean installs"); Store apps never show SmartScreen download warnings; no manual submission for consumers; Windows 11 Smart App Control may block unsigned files without positive reputation. — [SmartScreen reputation](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)
- Microsoft Store: individual developer registration is free (no fee, no credit card, ID + selfie), Microsoft hosts, signs ("sign your app for free") and auto-updates MSIX; Win32/WPF/WinForms/Electron/PWA/MAUI accepted. — [Windows Developer Blog, 2025-09-10](https://blogs.windows.com/windowsdeveloper/2025/09/10/free-developer-registration-for-individual-developers-on-microsoft-store/). Company accounts were $99 (search summary).
- Azure Artifact Signing (formerly Trusted Signing): Public Trust certs for organizations in US, Canada, EU, UK, Australia, NZ, Japan, South Korea, Singapore, Switzerland, Norway, Israel; individual developers must be in the US or Canada; needs a paid Azure subscription (not free/trial); identity validation via government ID/Verified ID (orgs 1-20 business days); no EV; SmartScreen reputation still accumulates; starts at $9.99/month (billed in full, not prorated). — [Quickstart](https://learn.microsoft.com/en-us/azure/artifact-signing/quickstart), [FAQ](https://learn.microsoft.com/en-us/azure/artifact-signing/faq), [SmartScreen doc](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation). Community reports of new warnings after CA changes on 2026-03-26 are anecdotal. — [Microsoft Q&A threads](https://learn.microsoft.com/en-us/answers/questions/5855805/artifact-signing-account-with-public-trust-certifi)
- SignPath Foundation (free for OSS): OSI-approved licence for all components with no proprietary parts, actively maintained and already released, no malware/PUP, verifiable automated builds, certificate issued to "SignPath Foundation", must display a code-signing-policy notice, MFA for all team members, manual approval of every release, initial reputation check (executables need verifiable reputation). — [SignPath terms](https://signpath.org/terms), [signpath.org](https://signpath.org/)
- Tauri updater: signature mandatory (minisign-style keypair, private key lost = cannot update existing installs), static JSON on GitHub Releases/S3 or dynamic server, Windows `installMode` passive (default)/basicUi/quiet, app exits during install, reuses NSIS/MSI installers. — [Tauri updater](https://v2.tauri.app/plugin/updater/). Tauri NSIS installs per-user by default (no admin); MSI only built on Windows. — [Windows installer](https://v2.tauri.app/distribute/windows-installer/)
- Velopack (Rust core; C#, Rust, JS, C++, Python SDKs): one command produces installer + update + delta packages, hosts on any static storage/GitHub Releases, migrates from Squirrel/ClickOnce; user testimonial of ~2 s apply/relaunch with no UAC (anecdote). Latest release 1.2.161 (2026-09-29). — [Velopack docs](https://docs.velopack.io/), [README](https://github.com/velopack/velopack), [releases](https://api.github.com/repos/velopack/velopack/releases?per_page=6)
- MSIX App Installer auto-update: Windows 10 2004+ and 11; check on launch/`HoursBetweenUpdateChecks`; `UpdateBlocksActivation`/`ShowPrompt` need 2021 schema; sideloaded MSIX needs a trusted signing certificate (inferred from signing requirement; see FAQ error table mention of MSIX publisher match). — [MSIX auto-update](https://learn.microsoft.com/en-us/windows/msix/app-installer/auto-update-and-repair--overview)
- Electron updates: built-in autoUpdater uses Squirrel.Windows (`RELEASES` + `.nupkg`), update.electronjs.org (public GitHub repo; default check at startup and every 10 min). — [Electron updates](https://www.electronjs.org/docs/latest/tutorial/updates)
- AV false positives: PyInstaller one-file bootloader/self-extractor flagged by signature scanners; unsigned binaries most at risk; submit to Microsoft and sign; Nuitka onefile has the same issue though non-onefile Nuitka avoids the stub; a vendor (biased) claim of 14/72 VirusTotal engines for PyInstaller onefile vs 0/72 for a Nuitka+native launcher. — [python.org thread](https://discuss.python.org/t/pyinstaller-false-positive/43171), [pydevtools Nuitka](https://pydevtools.com/handbook/reference/nuitka.md), [beatsyncpro (vendor)](https://beatsyncpro.ai/blog/why-pyinstaller-gets-antivirus-flags.html). Go binaries are also flagged as heuristics (Wacatac.B!ml) and fixed by signing — [golangbridge forum](https://forum.golangbridge.org/t/trojan-script-wacatac-b-ml-alert-on-windows-for-any-golang-build/35777). No Tauri/Wails-specific reports found.
- EDMCOverlay's installer is signed by its author, showing community precedent for signing small ED tools. — [EDMCOverlay](https://github.com/inorton/EDMCOverlay)

### Inferences
- For an open-source indie: Store (MSIX) for the "no warning" channel + SignPath-signed GitHub releases (NSIS/Velopack) for power users; Artifact Signing is only viable if the developer is in an eligible country or has a registered business. Prefer one-folder (not one-file) bundles for any Python build, and sign every release with the same identity.

### Gaps
- Real PyInstaller/Nuitka/Tauri installer sizes not measured; Velopack installer size and Azure pricing page figures (placeholders shown) not independently confirmed; Squirrel is superseded (Velopack docs) but no neutral Velopack vs MSIX comparison was found; Certum/other OSS certificates not researched.

## 7. Feature fit: embedded storage, JSON import, HTTP, ZeroMQ (EDDN)

### Takeaway
SQLite is available in every stack and import speed is bounded by JSON parsing rather than SQLite; a native (Rust/C#) importer can handle hundreds of MB in seconds-to-tens-of-seconds, Python an order of magnitude slower. EDDN's relay is a plain ZeroMQ SUB socket with zlib-compressed JSON; pure-Rust/NetMQ/pyzmq clients exist.

### Cited Findings
- SQLite insert benchmark (2019 MacBook Pro i5, 100M rows, tuned PRAGMAs `journal_mode=OFF`, `synchronous=0`, big cache, exclusive locking): Rust rusqlite prepared statements batch of 50 = 34.3 s (~2.9M rows/s); in-memory 29 s; CPython batched 510 s (8.5 min); PyPy 150 s; Rust sqlx (async) naive ~14 min vs rusqlite naive ~3 min. — [avi.im](https://avi.im/blag/2021/fast-sqlite-inserts/)
- SQLite WAL: readers do not block writers (good for UI reading while importing); same-host only; checkpoint default 1000 pages; for transactions above ~100 MB rollback journal may be faster; `synchronous=NORMAL` loses durability on power loss but not corruption. — [sqlite.org/wal](https://www.sqlite.org/wal.html)
- Python JSON parsing: orjson 2.2-6x faster than stdlib `json` loads on standard documents (e.g. twitter.json 453 -> 1889 ops/s; Python 3.11, Fedora 42). — [orjson](https://github.com/ijl/orjson)
- EDDN: connect ZeroMQ SUB to `tcp://eddn.edcd.io:9500`, subscribe to the empty topic (no server-side filtering), each message zlib-compressed UTF-8 JSON with `$schemaRef`, `header`, `message`; treat augmented fields as possibly wrong. Message volume is not documented. — [EDDN Developers.md](https://github.com/EDCD/EDDN/blob/live/docs/Developers.md)
- Client libs: Rust `zeromq` (pure Rust) 0.6.0 updated 2026-05-04; Rust `zmq` bindings last updated 2022-11 (needs libzmq); `rusqlite` 0.40.2 (2026-08-08); NetMQ (.NET, pure managed) 4.0.4.4; pyzmq 27.2.0. — [crates.io zeromq](https://crates.io/api/v1/crates/zeromq), [zmq](https://crates.io/api/v1/crates/zmq), [rusqlite](https://crates.io/api/v1/crates/rusqlite), [NuGet NetMQ](https://api.nuget.org/v3-flatcontainer/netmq/index.json), [PyPI pyzmq](https://pypi.org/pypi/pyzmq/json)
- Tauri/WebView2 recommends web messages over host objects, batched, to limit IPC CPU. — [WebView2 performance](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/performance)
- Own observation: the user's current journal set is 6 files / 2.4 MB (recent reinstall), so the "hundreds of MB" import case is about historical data the user may import. — own observation

### Inferences
- Import plan: stream line-by-line, parse with a fast parser, store raw JSON + a few indexed columns (event, timestamp, system), one big transaction per file with WAL + `synchronous=NORMAL`; run the import in a worker thread/process so the UI/game are not starved (low priority / EcoQoS). Python can still work (an import is one-off) but expect ~10x slower than Rust/.NET.

### Gaps
- Own import timing not run; no EDDN msgs/sec figure found; Microsoft.Data.Sqlite performance docs and System.Text.Json/simd-json numbers not retrieved; Go/Wails ZeroMQ options not researched.

## 8. Developer productivity and ecosystem maturity (UI libraries, charts, maps, theming, i18n, prior art)

### Takeaway
The web-frontend stacks (Tauri/Wails/Electron/pywebview/service+browser) have by far the richest data-grid/chart/map and sci-fi theming ecosystem; .NET (Avalonia/WPF) has good grids/charts (LiveCharts2 MIT) and is what most existing ED tools use; PySide6 is productive but LGPL/GPL module licensing needs care; Rust-native GUIs are still thin for data-heavy dashboards.

### Cited Findings
- Existing ED tools and their stacks: EDMarketConnector (Python, 1,275 stars, pushed 2026-10-01; uses tkinter per project history/uses watchdog), EDDI (C#, "companion application"), EDDiscovery (C#, 899 stars, "captain's log and 3D star map", pushed 2026-10-16), SrvSurvey (C#), EDDN (Python). — [EDMC](https://api.github.com/repos/EDCD/EDMarketConnector), [EDDI](https://api.github.com/repos/EDCD/EDDI), [EDDiscovery](https://api.github.com/repos/EDDiscovery/EDDiscovery), [SrvSurvey](https://api.github.com/repos/njthomson/SrvSurvey), [EDDN](https://api.github.com/repos/EDCD/EDDN)
- ED-Map.eu is a browser-based 3D galaxy map built with Three.js/WebGL. — [Frontier forum](https://forums.frontier.co.uk/goto/post?id=2601811). EDDiscovery's 3D renderer was not confirmed (OpenTK claim unverified).
- uPlot: ~50 KB, 166,650 points cold render in 25 ms, streaming 3,600 pts at 60 fps ~10% CPU/12.3 MB vs ECharts 70%/85 MB, Chart.js 40%/77 MB; heap 21 MB peak vs Plotly 104 MB, ApexCharts 175 MB, amCharts 147 MB (author's own benchmark, 2023, single machine). — [uPlot](https://github.com/leeoniya/uPlot)
- LiveCharts2 (MIT) supports Avalonia, WPF, WinUI, MAUI, Uno, Blazor WASM, WinForms; Skia drawing. — [LiveCharts2](https://github.com/beto-rodriguez/LiveCharts2)
- PySide6 is LGPLv3 (dynamic linking OK, must provide Qt source/offer); QtCharts and Qt Data Visualization are GPL/commercial modules; a PySide maintainer note advises commercial users not to use the community pip wheels. — [pythonguis.com PyQt6 vs PySide6 licensing](https://www.pythonguis.com/faq/licensing-differences-between-pyqt6-and-pyside6/), [Qt-project list](https://lists.qt-project.org/pipermail/pyside/2023-January/003256.html); distro metadata shows Qt Charts as GPL-3/LGPL-3/commercial. — [Arch qt6-charts](https://www.archlinux.org/packages/extra/x86_64/qt6-charts) (conflicting signals; verify with Qt)
- Slint is licensed GPL / royalty-free / commercial; desktop is a supported target; 1.18.1 released 2026-09-21. — [slint.dev](https://slint.dev/)
- egui: non-Latin text needs custom fonts via `set_fonts`; AccessKit accessibility on Windows/macOS; eframe backends glow/wgpu. — [egui README](https://github.com/emilk/egui)
- Avalonia 12 requires .NET 10-era toolchain, compiled bindings on by default; AOT needs `IsAotCompatible` and trimmer config. — [Avalonia 12](https://avaloniaui.net/blog/avalonia-12), [Native AOT docs](https://docs.avaloniaui.net/docs/deployment/native-aot)
- Wails v3 still beta (beta.30), Dioxus 0.8 alpha, iced 0.14 without 1.0, Windows App SDK 2.x with WinUI 3 under performance work: maturity ranking in Oct 2026: Electron > Tauri 2 (v3 in alpha) ≈ .NET WPF/Avalonia 12 ≈ Qt > Wails v2 > Flutter desktop > Rust-native GUIs. — version sources in section 1 (ranking is my inference)

### Inferences
- Most productive for a themed, data-dense UI with maps/charts: web frontend (React/Svelte/Solid + a virtualised grid + uPlot/ECharts + Three.js/deck.gl/Pixi for the galaxy map). If maximum frugality matters more than polish: Avalonia 12 or PySide6; if reuse of the ED community's ecosystem matters: .NET.
- "Local headless service + browser UI" maximises code reuse with the second-screen requirement but depends on the user's browser (Edge `--app` window measurement failed in my harness, so its cost vs WebView2 is unmeasured; Edge is installed on this PC).

### Gaps
- No ecosystem data for AG Grid/TanStack/Syncfusion licensing, Qt Quick 3D/Graphs, Flutter chart libraries, Bevy/wgpu galaxy maps; i18n tooling per stack (Qt Linguist, .NET resx, web i18next/Intl) not sourced; no third-party survey data on developer satisfaction for 2026.
