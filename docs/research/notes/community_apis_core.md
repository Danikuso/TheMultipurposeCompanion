# Community data networks and APIs for live Elite Dangerous galaxy data (EDDN, Inara, EDSM, Ardent Insight) — state as of 2026-10-17

Conventions: "own probe" = direct request/measurement made by the researcher on 2026-10-17 against the cited URL. "OUTDATED" marks documentation that is demonstrably stale. Game state at time of research: live client 4.4.1.1 (build r332841/r0), after the "Operations" update 4.4.0.0 of 30 June 2026.

## EDDN (Elite Dangerous Data Network): relay, upload, schemas, volume, etiquette

### Takeaway
EDDN is alive, actively maintained by EDCD and is the primary real-time firehose (about 1.08 million validated messages per UTC day, about 13 msg/s, about 10-12 kB/s compressed). Subscribing from a desktop app is trivially cheap (measured about 0.2% of one CPU core in Python including JSON parsing); there is no server-side filtering, no history, and the relay restarts weekly, so the client must filter by `$schemaRef`, reconnect, and keep its own local cache.

### Cited Findings
**Endpoints and protocol**
- Subscriber relay: `tcp://eddn.edcd.io:9500`; ZeroMQ SUB; subscribe to the empty topic `''` if your library needs it; each message is zlib-compressed, decompress then parse JSON; use `$schemaRef` to identify the schema. — [Developers.md (live)](https://github.com/EDCD/EDDN/blob/live/docs/Developers.md)
- Server-side subscription filtering is NOT supported ("old version of ZeroMQ"); any topic filter drops messages client-side. Schema validation is done at the Gateway, so consumers need not validate; messages failing validation are not forwarded. — [Developers.md](https://github.com/EDCD/EDDN/blob/live/docs/Developers.md)
- Own probe: the relay greets as ZMTP 3.1, Socket-Type XPUB, NULL mechanism; a raw ZMTP SUB client with an empty subscription received a continuous stream; each message arrives as a single zlib frame. — [relay tcp://eddn.edcd.io:9500, see Developers.md](https://github.com/EDCD/EDDN/blob/live/docs/Developers.md)
- Relay code: PUB socket with `SNDHWM` 500 (slow subscribers can lose messages), uploader IP is stripped and `uploaderID` is scrambled before re-broadcast. — [Relay.py (live)](https://github.com/EDCD/EDDN/blob/live/src/eddn/Relay.py)
- Relay de-duplication was DISABLED on 2026-03-22 (`RELAY_DUPLICATE_MAX_MINUTES` 15 -> `False`), so identical data from several uploaders now reaches subscribers; the live Settings.py shows `False`. — [commit d9204abd](https://github.com/EDCD/EDDN/commit/d9204abd); [Settings.py (live)](https://github.com/EDCD/EDDN/blob/live/src/eddn/conf/Settings.py)
- Live service "should always be running" and is restarted automatically every Thursday 07:06:00 UTC; the service stores no data, it is a live stream only. — [EDDN README](https://github.com/EDCD/EDDN)
- Upload: `POST https://eddn.edcd.io:4430/upload/` (trailing slash required; plain HTTP gives 400; HTTP/1.1 only, HTTP/2 unsupported; no query parameters); optional gzip body with `Content-Encoding: gzip`; form-encoded uploads unsupported since 2022-06-16; body limit 1 MiB measured on the compressed size. — [Developers.md](https://github.com/EDCD/EDDN/blob/live/docs/Developers.md) (the page's `Content-Type` spelling "applicaton/json" is a typo; use `application/json`)
- Beta: upload `https://beta.eddn.edcd.io:4431/upload/`, listener `tcp://beta.eddn.edcd.io:9510`; Dev: `https://dev.eddn.edcd.io:4432/upload/`, listener `tcp://dev.eddn.edcd.io:9520`; both normally not available to the public (ask in #eddn on the EDCD Discord). — [EDDN README](https://github.com/EDCD/EDDN)
- Response codes: 200 "OK"; 400 "FAIL: ..." (zlib/JSON/schema validation); 426 outdated schema; 408/503 from the reverse proxy; 413 payload too large. Do NOT retry 400/426; wait at least 1 minute before any retry; one bad message must not block the queue; "no data is better than bad data". — [Developers.md](https://github.com/EDCD/EDDN/blob/live/docs/Developers.md)

**Sender requirements (etiquette)**
- Envelope: `$schemaRef`, `header`, `message`. Header: `uploaderID` (preferably Cmdr name; EDDN obfuscates it), unique `softwareName`, meaningful `softwareVersion` (bump on any content change), `gameversion` and `gamebuild` (from `Fileheader`, else `LoadGame`; CAPI sources use `CAPI-Live-<endpoint>` / `CAPI-Legacy-<endpoint>`; send empty string if unknown; never strip whitespace of gamebuild, e.g. `"r332841/r0 "`). The Gateway adds `gatewayTimestamp` itself (do not send it). — [Developers.md](https://github.com/EDCD/EDDN/blob/live/docs/Developers.md); [README-EDDN-schemas.md](https://github.com/EDCD/EDDN/blob/live/schemas/README-EDDN-schemas.md)
- Must not send alpha/beta game data to the live schemas; append `/test` to `$schemaRef` (e.g. `.../shipyard/2/test`) when testing. — [Developers.md](https://github.com/EDCD/EDDN/blob/live/docs/Developers.md)
- `horizons` and `odyssey` booleans must come only from the `LoadGame` event (never `Fileheader`); if unknown, omit the key (no null, no default false). — [Developers.md](https://github.com/EDCD/EDDN/blob/live/docs/Developers.md)
- No Cmdr-specific data (only `uploaderID`, `horizons`, `odyssey` allowed); remove every key ending `_Localised`; schema-specific elisions (e.g. Docked: `Wanted`, `ActiveFine`, `CockpitBreach`; FSDJump: `Wanted`, `BoostUsed`, `FuelLevel`, `FuelUsed`, `JumpDist`, faction `MyReputation` etc.; commodity: drop `StationType`, `Producer`, `Rare`, `id`, `Category`, skip NonMarketable and items with non-empty legality). — [Developers.md](https://github.com/EDCD/EDDN/blob/live/docs/Developers.md); [journal-README](https://github.com/EDCD/EDDN/blob/live/schemas/journal-README.md); [commodity-README](https://github.com/EDCD/EDDN/blob/live/schemas/commodity-README.md)
- Where a schema requires augmentation with `StarSystem`/`SystemAddress`/`StarPos`, cross-check against the last `Location`/`FSDJump`/`CarrierJump` and drop the message on mismatch (known game bug can stop journal writing). — [Developers.md](https://github.com/EDCD/EDDN/blob/live/docs/Developers.md)
- CAPI data is "not recommended" as a source; if used, check CAPI lag (`commander.docked` true and station/system names match last Docked/Location, else abort). — [Developers.md](https://github.com/EDCD/EDDN/blob/live/docs/Developers.md)
- Legacy-galaxy handling: EDDN does not forbid Legacy data but defines `CAPI-Legacy-*` markers so listeners can separate it; Inara and EDSM explicitly refuse Legacy data (see their sections). — [Developers.md](https://github.com/EDCD/EDDN/blob/live/docs/Developers.md)
- `fsssignaldiscovered` requires coalescing contiguous `FSSSignalDiscovered` events into one `signals` array. — [fsssignaldiscovered-README](https://github.com/EDCD/EDDN/blob/live/schemas/fsssignaldiscovered-README.md)

**Real-world sender pattern (EDMarketConnector eddn.py)**
- Uses a persistent SQLite queue (`eddn_queue-v1.db`), HTTP timeout 10 s, retry pass every 300,000 ms, 400 ms between replayed messages (about 2 msg/s), startup delay 10 s, `softwareName` = `"<app> [<OS>]"`, `uploaderID` = Cmdr name, `/test` appended when the game is beta; drops a message on HTTP 400. It currently sends approachsettlement, codexentry, commodity/3, dockingdenied, dockinggranted, fcmaterials_capi, fcmaterials_journal, fssallbodiesfound, fssbodysignals, fssdiscoveryscan, fsssignaldiscovered, journal/1, navbeaconscan, navroute, outfitting/2, scanbarycentre, shipyard/2 — not yet scanorganic/1 or outfitting/3. EDMC latest release 6.1.2 (2026-01-29). — [eddn.py](https://github.com/EDCD/EDMarketConnector/blob/main/plugins/eddn.py); [EDMC releases](https://github.com/EDCD/EDMarketConnector/releases)
- Third-party archive of EDDN captures and an EDDN lookup exist at edgalaxydata.space (also hosts EDSM/Spansh/EDDB captures). — [edgalaxydata.space](https://edgalaxydata.space/)

### Inferences
- Cheap client-side filtering: peek at `$schemaRef` after one `zlib.decompress` + `json.loads` (or substring-test the decompressed bytes before parsing); drop `/test` refs and any `gameversion` starting `CAPI-Legacy`/`3.8`. At about 13 msg/s and about 2.6 kB decompressed per message the work is negligible next to a running game; memory is bounded if the socket is drained promptly (relay HWM 500).
- Because the stream has no replay, a companion must maintain its own SQLite/dict cache (market by marketId, systems by SystemAddress) and tolerate a gap at the weekly Thursday 07:06 UTC restart and during reconnects.
- For "where to sell X now" a locally built cache from `commodity/3` is the freshest source, but it only fills as fast as players dock; Ardent does exactly this server-side (see Ardent section).
- Uploading is optional for a companion; if it does upload it must replicate EDMC-grade rules (augmentation cross-checks, elisions, queue/retry, gameversion/gamebuild). Piggy-backing on EDMC/EDDiscovery already uploading the same journal would double-send; this is an inference from the Monitor listing EDMC/EDDiscovery as the main uploaders.
- The Monitor shows `/test` traffic of about 0.16% of volume; whether the relay forwards `/test` messages to subscribers is unconfirmed (none seen in about 2,850 sampled messages), so filtering them is prudent.

### Gaps
- Diurnal variation of volume was not measured over 24 h (only the daily total and two samples around 00:40 UTC).
- Whether `/test` messages are relayed to public subscribers: Gateway code pushes all validated schemas including `/test`, but empirical confirmation is missing.
- Authoritative list of EDDN schemas currently deployed: no single official page; derived from schema URLs, Monitor, Settings.py (which lags). The EDCD Discord (#eddn) announcements were not accessible.
- Hosting/ownership details of EDDN infrastructure beyond "hosting by EDCD" were not established (docs folder contains historic "Anthor-VPS" notes for Debian Stretch; not treated as current).
- No SLA or published uptime history for the relay was found.

## Inara: API v1 (inapi), authentication, events, limits, terms, status

### Takeaway
Inara API is alive and actively gatekeeping: every app name must be whitelisted by the site owner (Artie), users supply personal API keys (or whitelisted apps use a generic key for the two read events), and the pinned rule is at most two requests per minute with batching. It is mainly a write/sync API for the commander's own profile; reads are limited to `getCommanderProfile` and `getCommunityGoalsRecent`, and markets, stations, systems and minor-faction data are explicitly NOT available.

### Cited Findings
- Single endpoint: POST JSON (uncompressed) to `https://inara.cz/inapi/v1/` with `Content-Type: application/json`; request and response each have `header` and `events`; results return in the order sent; if nothing returns, retry after a reasonable delay. — [Inara API dev guide](https://inara.cz/elite/inara-api-devguide); [Inara API docs](https://inara.cz/elite/inara-api-docs/)
- Header fields: `appName`, `appVersion` (semver-like string, version control may apply), `isBeingDeveloped` (true skips global updates such as `setCommunityGoal`; newly whitelisted dev apps have it set server-side by default), `APIkey` (user's personal key or generic application key for general read-only events), `commanderName` (in-game name; recommended whenever a generic key is not used), `commanderFrontierID` (F123456 form, from journals since 3.3). Events carry `eventName`, `eventTimestamp` (ISO 8601; should not be older than 30 days), optional `eventCustomID`, `eventData`. — [Inara API docs](https://inara.cz/elite/inara-api-docs/)
- Status codes: event/header `eventStatus` 200 OK, 202 warning (e.g. multiple matches), 204 soft error/no results, 400 error (event skipped or whole batch cancelled on bad authorization). — [Inara API docs](https://inara.cz/elite/inara-api-docs/)
- Whitelisting is mandatory: send the developer the exact application name, what it does, a short description for the public app list, and a homepage/download URL; "it needs to be white-listed first. It is not meant to exclude anyone". Apps "evidently based on some AI chatbot summary ... will be simply ignored". — [Inara API dev guide](https://inara.cz/elite/inara-api-devguide)
- Whitelisting is handled publicly in the API forum thread: in Sept-Oct 2026 Artie whitelisted COVAS (renamed "Pharos Vagantem", name had to change because COVAS is an in-game term), "NXS Workspace", the renamed "Galactic Companion Hub" (asked to drop the generic name "ED Companion" because it is too generic and was Frontier's app name, and told that architect status and commodity search are not in the API), ARCONEDIA, CarrierNavigator and pibe38-commander-log; turnaround observed from hours to about 12 days; whitelisting returns the app's generic API key. — [Inara API forum thread, page 42](https://inara.cz/elite/board-thread/7049?page=42)
- Personal API keys are generated by each user in Inara Settings; most tools require one. — [Inara API overview](https://inara.cz/elite/inara-api/)
- Rate limit (sticky note in the API forum thread): "please ensure your apps are doing TWO requests per minute AT MAXIMUM"; bots and non-demanding apps keep the previous rate; other limits can be requested by PM. The dev guide adds "be polite", batch events (session start/end, Docked, FSDJump), cache, and warns that excessive requests may lead to API key invalidation. — [Inara API forum thread](https://inara.cz/elite/board-thread/7049?page=42); [dev guide](https://inara.cz/elite/inara-api-devguide)
- Do: Live game data only (Odyssey, Horizons 4.0, future updates). Don't: send Legacy (Horizons 3.8) data, beta data (allowed only on test accounts), one-event-per-request spam, or repeated identical events. Developer may disallow apps/keys with many errors, rule breaches, or misuse "like mass data scraping of commanders information, attempts to 'spy' on others". — [Inara API dev guide](https://inara.cz/elite/inara-api-devguide)
- Not provided by the API: "It does not include markets, minor faction influences, star systems, stations, or similar outputs." — [dev guide](https://inara.cz/elite/inara-api-devguide)
- Read events: only `getCommanderProfile` (generic key allowed; input `searchName`, any Cmdr or own profile with personal key; returns userID/userName/commanderName, `commanderRanksPilot` with progress for combat/trade/exploration/cqc/empire/federation, preferredAllegianceName, preferredPowerName, commanderMainShip, commanderSquadron, preferredGameRole, avatar/inara URLs, `dataImportActive`, `otherNamesFound`; NO location) and `getCommunityGoalsRecent` (generic key; empty eventData). — [Inara API docs](https://inara.cz/elite/inara-api-docs/)
- Write events documented: addCommanderFriend, delCommanderFriend, addCommanderPermit (permit list "not implemented on Inara yet"), setCommanderCredits, setCommanderGameStatistics, setCommanderRankPilot/Engineer/Power, setCommanderReputationMajorFaction/MinorFaction, add/del/set/reset CommanderInventory*, CommanderInventoryCargo*, CommanderInventoryMaterials*, setCommanderStorageModules, addCommanderShip, delCommanderShip, setCommanderShip, setCommanderShipLoadout, setCommanderShipTransfer, set/update/delCommanderSuitLoadout, addCommanderTravelCarrierJump/Dock/FSDJump/Land, setCommanderTravelLocation, addCommanderMission, setCommanderMissionAbandoned/Completed/Failed, addCommanderCombatDeath/Interdicted/Interdiction/InterdictionEscape/Kill (PvP only), setCommanderCommunityGoalProgress, setCommunityGoal. — [Inara API docs](https://inara.cz/elite/inara-api-docs/)
- Documented cautions: `setCommanderInventoryMaterials` and `setCommanderGameStatistics` replace the full set; avoid sending Docked at session start (floods flight log); `delCommanderShip` may fail for manually-entered ships; credits should only be set when sure (wages not in journals). — [Inara API docs](https://inara.cz/elite/inara-api-docs/); [Inara API overview](https://inara.cz/elite/inara-api/)
- Terms of Service: personal, non-commercial use; no copying/republishing Inara content; no automated means (bots, scrapers, crawlers) to access or collect content "in a way that violates these Terms or unreasonably interferes with the Service, without our permission"; governed by Czech law. — [Inara Terms of Service and Privacy Policy](https://inara.cz/elite/policies/)
- Status: API forum has live whitelisting traffic through 12 Oct 2026; the overview lists EDMC (5.6.0+), EDDI, EDDiscovery and EDDLite as supporting apps. — [API forum thread](https://inara.cz/elite/board-thread/7049?page=42); [overview](https://inara.cz/elite/inara-api/)
- Real-world sender (EDMC inara.py): `TARGET_URL = 'https://inara.cz/inapi/v1/'`, one POST per commander per worker cycle with `WORKER_WAIT_TIME = 35` s, timeout 20 s, per-commander personal keys, `filter_events` to collapse superseded ship/loadout/storage/CG events, credits updates only when delta > 5% and > 10,000,000, skips Legacy events and test systems (CQC, Training, Destination). — [inara.py](https://github.com/EDCD/EDMarketConnector/blob/main/plugins/inara.py)

### Inferences
- A new companion app needs: a distinct non-generic app name (avoid "ED Companion", in-game terms, Frontier names), a forum request to Artie before release, per-user personal key entry in settings, a request scheduler capped well under 2 req/min with batching/caching (EDMC's 35 s flush is a safe reference), and a Live-only guard.
- Inara cannot serve as a market/station/system source, and it provides no commander location read, so "friends' location" cannot come from Inara's API.
- Cheapest use for a read-only desktop companion: `getCommanderProfile` for ranks/squadron/power with the whitelisted generic key, cached for minutes; reading other Cmdrs' profiles in bulk would conflict with the anti-scraping/anti-spying wording.

### Gaps
- Exact numeric limits beyond the "two requests per minute" sticky note (and whether it differs by key type) are not published; the sticky note's date is not shown.
- The Inara docs page lacks a changelog, so newly added 2025-2026 events could not be diffed.
- Whitelisting response time is only anecdotal (forum samples); no formal SLA.
- No Inara ownership or maintenance-change information beyond "Artie" answering as the API owner in 2026.

## EDSM (Elite Dangerous Star Map): API endpoints, journal upload, limits, dumps, 2024-2026 status

### Takeaway
EDSM is still alive and maintained by its creator Anthor (nightly dumps generated 2026-10-16, issue replies in August 2026) but is strained: documentation is mostly 2019-2022 vintage, endpoints intermittently overloaded (empty results then 503), Cloudflare bot challenges and 403s since April 2026, and rate limiting moved to Cloudflare in August 2026 (10 requests per 10 s). Best used for system/faction/traffic/deaths lookups, per-station market/shipyard/outfitting by marketId, commander flight-log position (opt-in), and bulk nightly dumps; the journal upload API requires the user's EDSM API key.

### Cited Findings
**Endpoints (documentation pages)**
- `api-v1` (revision Oct 6 2020): `GET https://www.edsm.net/api-v1/system` (flags showId/showCoordinates/showPermit/showInformation/showPrimaryStar, includeHidden), `/systems` (name prefix or array; `startDateTime`/`endDateTime` max interval 3 days), `/sphere-systems` (radius max 100 ly), `/cube-systems` (size max 200). The menu link "API Systems v1" resolves to `/en/api-v1` (`/en/api-systems-v1` is 404). — [EDSM API Systems v1](https://www.edsm.net/en/api-v1)
- `api-system-v1` (revision Mar 20 2019, all GET): `/bodies`, `/estimated-value`, `/stations`, `/stations/market`, `/stations/shipyard`, `/stations/outfitting` (marketId alone is enough), `/factions` (`showHistory=1`), `/traffic` (total/week/day plus ship breakdown), `/deaths` (total/week/day). — [EDSM API System v1](https://www.edsm.net/en/api-system-v1)

- EDSM's traffic/deaths numbers only reflect Cmdrs who feed EDSM (not the whole galaxy); this is inferred from how EDSM ingests data, not stated in the docs, and should not be presented as galaxy-wide danger.

- Sending journal events to EDSM duplicates what EDMC/EDDiscovery do; the 300 s duplicate cache (code 103) suggests multi-tool use is tolerated.

## Ardent Insight (ardent-insight.com, Iain Collins): API, data freshness, repos, status 2026

### Takeaway
Ardent is alive and actively updated (API v6.4.1, collector/website pushes in September 2026, live stats stamped 2026-10-16). It is an EDDN-fed, anonymous, rate-limit-free REST API (AGPL-3.0) that is the best single source for "where to sell/buy commodity X near me" and "nearest station with service Y", but its default parameters can return stale entries and it has no powerplay, ship-specific or module-specific search.

### Inferences
- Because Ardent only mirrors what players upload to EDDN, freshness equals "last docked-and-uploaded"; hot areas update within minutes, remote or rarely visited stations can be weeks old. Always pass `maxDaysAgo` (e.g. 1-3 days for trading), `fleetCarriers=false` unless carriers are wanted, `minVolume`, and filter out construction-site/colonisation entries.
- Edge cache `s-maxage=300` means identical queries are at most about 5 minutes stale, so polling more often than every 1-5 minutes gives nothing; a companion should cache per (system, commodity, params).
- Reasonable for a desktop app: anonymous REST with its own cache, modest request volume and a descriptive User-Agent; for offline/bulk analytics use the weekly SQLite dumps instead of hammering the API.
- Single-maintainer project (Iain Collins); operational risk is bus factor and the dependency on EDSM for `/status` and `/bodies`; the README itself says internal logic and defaults may change.

### Gaps
- No published uptime history or SLA; no formal terms of use beyond README/AGPL and "respectful use".
- Exact operator contact and funding model not stated on the pages read.
- Ardent collector internals (which EDDN schemas it ingests) were not read; only its stated purpose ("saves data submitted to the Elite Dangerous Data Network").
- `maxDaysAgo` behaviour differs from the README on at least the nearby routes; the cause (README stale vs. bug) is unconfirmed.
- Search by specific ship or module is not in the route list; no endpoint found for it.

## Which service best answers each companion-app question

### Takeaway
Use Ardent for market and nearest-service questions, EDSM for system/faction/traffic/deaths/friend-position data, EDDN as the real-time feed (for the player's own surroundings and for building a local cache), and Inara only for syncing/reading the commander's own profile. For "which station sells ship Z / module W" none of the four has a search API; Spansh (outside the assigned scope) does.

### Cited Findings
- "Where to sell/buy commodity X near me now": Ardent `/system/name/{here}/commodity/name/{x}/nearby/imports|exports` (sell = imports ordered by highest price; buy = exports ordered by lowest price), with `maxDaysAgo`, `fleetCarriers`, `minVolume`, `maxDistance`. — [ardent-api README](https://github.com/iaincollins/ardent-api)
  - EDSM only gives per-station market lists (`stations/market`, no timestamp, no search). — [API System v1](https://www.edsm.net/en/api-system-v1)
  - Inara API excludes markets entirely. — [dev guide](https://inara.cz/elite/inara-api-devguide)
  - EDDN `commodity/3` is the raw live feed behind Ardent (51,509 messages on 2026-10-16). — [EDDN Monitor](https://eddn.edcd.io/)
- "Nearest station with service Y": Ardent `/nearest/{interstellar-factors|material-trader|technology-broker|black-market|universal-cartographics|refuel|repair|shipyard|outfitting|search-and-rescue}` with `minLandingPadSize`. — [systems.js](https://github.com/iaincollins/ardent-api/blob/main/router/api/systems.js)
- "Shipyard with ship Z / outfitting with module W": Ardent only returns stations that have a shipyard/outfitting (generic). EDSM gives the ship/module list per station (`stations/shipyard`, `stations/outfitting`) but cannot search. EDDN carries per-station `shipyard/2` and `outfitting/2|3` messages to build your own index (16,718 and 27,237 messages on 2026-10-16). Inara's website has an outfitting search but its API excludes it. Pointer outside scope, verified by own probe: Spansh `POST https://spansh.co.uk/api/stations/search` with a `filters.ships` entry returned stations with shipyard timestamps; module/service/commodity filters were not tested. — [EDSM docs](https://www.edsm.net/en/api-system-v1); [EDDN Monitor](https://eddn.edcd.io/); [Inara dev guide](https://inara.cz/elite/inara-api-devguide); [Spansh search](https://spansh.co.uk/api/stations/search)
- "System info / factions / states / powerplay": EDSM `api-v1/system` (allegiance, government, controlling faction, faction state, population, security, economy), `api-system-v1/factions` (influence, state, active/pending/recovering states, optional history, `lastUpdate`), `api-system-v1/stations`; powerplay only via the daily `powerPlay.json.gz` dump. Ardent has only a pass-through `/status` (no powerplay; issues #4 and #10 open). Live EDDN `journal/1` `FSDJump`/`Location` messages carry the same system data in real time. — [EDSM docs](https://www.edsm.net/en/api-v1); [nightly dumps](https://www.edsm.net/en/nightly-dumps); [ardent-api issues](https://github.com/iaincollins/ardent-api/issues); [EDDN journal README](https://github.com/EDCD/EDDN/blob/live/schemas/journal-README.md)
- "Traffic / danger in a system": EDSM `api-system-v1/traffic` (total/week/day with ship-type breakdown) and `deaths` (total/week/day); no equivalent in Ardent, Inara or EDDN. — [API System v1](https://www.edsm.net/en/api-system-v1)
- "Commander location sharing with friends": EDSM `api-logs-v1/get-position` (works for Cmdrs with public profile sharing logs/map, or with that Cmdr's API key) plus `get-logs`; Inara's `getCommanderProfile` has no location and the guide forbids "spying"; EDDN anonymises uploaderID and forbids Cmdr-specific data. A privacy-respecting friends feature would need the app's own opt-in channel. — [API Logs v1](https://www.edsm.net/en/api-logs-v1); [Inara docs](https://inara.cz/elite/inara-api-docs/); [Inara dev guide](https://inara.cz/elite/inara-api-devguide); [Relay.py](https://github.com/EDCD/EDDN/blob/live/src/eddn/Relay.py)
- Commander-own profile sync/rank reading: Inara write events (`setCommanderShip`, `setCommanderInventoryMaterials`, `addCommanderTravelFSDJump`, ...) and `getCommanderProfile`; EDSM `get-ranks`/`get-credits`/`get-materials` with the user's EDSM key. — [Inara docs](https://inara.cz/elite/inara-api-docs/); [API Commander v1](https://www.edsm.net/en/api-commander-v1)

### Inferences
- Suggested split for a desktop companion: (1) read the local journal for the player's own state; (2) optional EDDN SUB listener with a local cache for nearby live market/system updates (cost is negligible); (3) Ardent REST for "best price / nearest service" queries with explicit `maxDaysAgo`; (4) EDSM REST for factions/traffic/deaths/position with a User-Agent and polite throttling; (5) Inara only as an opt-in sync, after whitelisting, with personal keys and at most 2 req/min.
- Dependencies between services create correlated failure: Ardent `/status` and `/bodies` depend on EDSM; EDSM, Inara, Ardent and the EDDN sender ecosystem all ultimately depend on players' EDMC/EDDiscovery uploads (EDMC + EDDiscovery = about 74% of EDDN messages on 2026-10-16: 801,736 of 1,078,983).

### Gaps
- Spansh's API (station search by modules/services/commodities, rate rules, status) was only touched by one probe and is not otherwise covered; another researcher may cover it.
- No source was found that quantifies end-to-end freshness differences between EDSM, Ardent and Inara for the same station.
- Friend/wing presence data from Frontier's own services (CAPI) is out of this assignment's scope.
